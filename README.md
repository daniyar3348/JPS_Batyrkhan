# Платформа научного журнала

Система по образцу Open Journal Systems: подача рукописей, рецензирование, редактура, публикация.
Архитектура описана в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Что готово

### Этап 5 — производство и публикация

- **Редактура.** После принятия редактор назначает литературного редактора.
  - Литредактор, редакторы и авторы обмениваются версиями текста на вкладке «Copyediting».
  - Литредактор не видит рецензий и переписки по рецензированию.
  - После принятия метаданные (название, аннотацию, авторов) правят редакторы, автор уже не может.
- **Производство.** Решение «Send to production» переводит статью в вёрстку.
  - В этот момент резервируется DOI, чтобы его можно было напечатать в гранках.
  - Верстальщик загружает исходники вёрстки и гранки: PDF, HTML, XML или EPUB, то есть файлы для читателей. Корректор их читает.
  - У литредактора, верстальщика и корректора своя страница «Production work»; письмо о назначении приходит каждому.
- **Выпуски.** Выпуск задаётся томом, номером, годом и названием, например `Vol. 1 No. 1 (2026)`.
  - Статьи внутри выпуска идут в порядке разделов; внутри раздела порядок задаёт редактор.
  - Публикация выпуска выпускает все запланированные в него статьи сразу. Если хотя бы одна не готова, не выходит ничего.
  - Один выпуск отмечается текущим: его показывает главная страница сайта.
- **Публикация статьи.** На вкладке «Publication» видно, чего не хватает:
  - выпуска;
  - гранок;
  - оплаты, если журнал берёт плату;
  - префикса DOI;
  - свободного адреса на сайте.

  Если выпуск ещё не вышел, статья планируется в него. Если выпуск уже опубликован, статья появляется сразу (непрерывная публикация). Публиковать может только редактор с правом решения. Авторам приходит письмо со ссылкой на DOI.
- **Версии.** Опубликованная версия не меняется. Исправление оформляется как новая версия с пояснением.
  - Читатели видят все версии, файлы старых версий остаются доступными.
  - Метаданные заново отправляются в Crossref.
- **DOI и Crossref.** DOI строится из префикса и шаблона, например `10.12345/jrn.2026.0042`. При публикации worker:
  1. собирает XML по схеме Crossref 5.3.1: авторы с ORCID и аффилиациями, аннотация, лицензия, литература, ссылки на полный текст для Similarity Check;
  2. отправляет его в Crossref;
  3. затем проверяет результат обработки.

  Каждая отправка с ответом Crossref видна на странице «DOI registration», её можно повторить.
- **Витрина.** При публикации собирается снимок статьи. Публичный API и OAI-PMH читают только его, а не редакционные таблицы.
- **Публичный API** (`/public/v1`):
  - `issues`, `issues/current`, `issues/{id}`, `issues/{том}/{номер}`;
  - `articles`, `articles/{адрес}`;
  - `search?q=` — полнотекстовый поиск PostgreSQL;
  - `sections`, `galleys/{id}/download`.

  Ответы кэшируются: заголовки `Cache-Control` плюс микрокэш nginx.
- **OAI-PMH** (`/oai`) — все шесть глаголов, Dublin Core, наборы по журналу и разделам, токены продолжения. Через него статьи забирают BASE, OpenAIRE, CyberLeninka и другие индексаторы.
- **Сайт журнала** (этап 6) после публикации получает подписанный HMAC запрос со списком страниц, которые нужно обновить.

**Регистрация DOI на сервере** (`JPS_CROSSREF_MODE`):
- `disabled` — DOI присваиваются, но не регистрируются.
- `fake` — для разработки: отправка считается успешной, в Crossref ничего не уходит.
- `test` — тестовая система Crossref (`test.crossref.org`): проверяет XML, но ничего не регистрирует.
- `production` — настоящая регистрация.

Для `test` и `production` нужны учётная запись Crossref (`JPS_CROSSREF_USERNAME`, `JPS_CROSSREF_PASSWORD`), префикс и ISSN журнала.
Обмен с Crossref проверен на подменённых ответах в документированных форматах. Отсюда сервер Crossref недоступен, поэтому до запуска нужно отправить пробный DOI в тестовую систему с учётной записью журнала.

### Этап 4 — плата за публикацию

- **Счёт выставляется только после принятия статьи**, в той же транзакции, что и решение «Принять».
  - Номер вида `INV-2026-0001`.
  - Сумма по тарифу журнала или раздела, со скидкой по одобренной льготе и НДС.
  - Срок оплаты; автору приходит письмо со ссылкой.
- **Оплата.**
  - Картой: через страницу провайдера, данные карты на сервер журнала не попадают.
  - PayPal.
  - Банковским переводом по реквизитам из счёта; поступление подтверждает финансовый менеджер.
- **Надёжность.**
  - Платёж засчитывается только по подписанному уведомлению провайдера или по ответу его API, но не по возврату браузера.
  - Повторное уведомление ничего не меняет.
  - Платёж на другую сумму не закрывает счёт, финансовый менеджер получает письмо.
- **Возвраты**, полные и частичные. Онлайн-платежи возвращаются через провайдера; возврат перевода только фиксируется.
- **Аннулирование счёта и выставление нового.**
- **Плательщик:** автор может переоформить счёт на свой университет.
- **Счёт и квитанция в PDF.** Используется шрифт с кириллицей, так что казахские и русские имена печатаются правильно.
- **Льготы.**
  - Автор может попросить снизить или снять плату в любой момент до оплаты.
  - Решает финансовый менеджер.
  - Полная льгота закрывает счёт, частичная уменьшает сумму.
- **Независимость редакции (§8.5 архитектуры).**
  - Редакторы и рецензенты не видят ни счетов, ни льгот.
  - Письма об оплате не попадают в журнал писем по рукописи.
  - После принятия редактор видит только «плата внесена — можно публиковать / нет».
  - Импорт-линтер следит, чтобы модуль рецензирования и модуль платежей не зависели друг от друга.
- **Автоматика.**
  - Напоминания об оплате, каждое один раз.
  - Ежедневная сверка с провайдерами: ловит пропущенные уведомления, закрывает брошенные оплаты и сообщает о проблемах финансовому менеджеру.
- **Страницы.**
  - Автор: вкладка «Publication fee» и страница возврата после оплаты.
  - Финансовый менеджер: счета, карточка счёта, заявки на льготу, настройки оплаты.

**Способы оплаты на сервере:**
- **Тестовый провайдер** (`JPS_PAYMENTS_TEST_PROVIDER`, только для разработки): изображает страницу оплаты картой и присылает подписанные уведомления. В production приложение с ним не запустится.
- **PayPal** подключается ключами `JPS_PAYPAL_*`.
  - Адаптер проверен на документированных форматах API с подменёнными ответами; до запуска его нужно проверить в песочнице PayPal с ключами журнала.
  - PayPal не принимает тенге: при счетах в KZT способ показывается недоступным с объяснением.
- **Казахстанский эквайринг для карт** ещё не подключён.
  - Нужен выбор провайдера (Halyk ePay, TipTop Pay, Freedom Pay), договор и тестовые ключи.
  - Адаптер добавляется одним файлом в `payments/providers/`, остальной код не меняется.

### Этап 3 — редакционный процесс и рецензирование

- **Решения редактора** по одной таблице переходов:
  - отправить на рецензирование;
  - принять или отклонить (в том числе без рецензирования);
  - запросить исправления;
  - отправить на доработку с новым раундом рецензирования;
  - начать новый раунд;
  - восстановить отклонённую рукопись (с указанием причины).

  Перед каждым решением редактор видит письмо автору по шаблону и может его изменить. В письмо после рецензирования автоматически входят комментарии рецензентов для авторов («Reviewer 1», «Reviewer 2»…), без имён и без конфиденциальных частей.
- **Редакторы рукописи.**
  - Редакторы раздела назначаются автоматически при подаче; главный редактор может добавить или снять редактора.
  - Редактор с правом «только рекомендация» не принимает решения сам: он отправляет рекомендацию, и решающие редакторы получают письмо.
- **Рецензирование.**
  - Раунды; файлы для рецензентов (копии, из свойств которых удалены имена авторов).
  - Приглашение рецензента из списка журнала или нового человека: он получает учётную запись и отдельное письмо для установки пароля.
  - Сроки ответа и рецензии; приглашение можно отменить, а отказавшегося рецензента пригласить повторно.
  - Автоматические напоминания: каждое приходит один раз, при переносе срока они снова становятся актуальными. Редактор может отправить напоминание и вручную.
  - Форма рецензии: вопросы, видимые автору или только редакции. Рекомендация, комментарии для авторов и конфиденциальные для редактора, файлы рецензента; из их свойств удаляется имя рецензента.
  - Оценка рецензии редактором (1–5) и благодарственное письмо.
- **Подсказка рецензентов.**
  - Совпадение научных интересов с ключевыми словами, история рецензий, текущая нагрузка.
  - Авторы, редакторы, уже приглашённые и заявившие конфликт интересов исключаются.
  - Предупреждения: та же организация, что у автора; отказ в прошлом раунде.
- **Слепое рецензирование** (двойное, одинарное, открытое).
  - Рецензент видит рукопись без имён авторов и без сопроводительного письма, а файлы — только после согласия.
  - Автор видит рецензии только после решения редактора, подписанные «Reviewer N».
  - Это обеспечивает сервер: скрытые поля не попадают в ответ API.
- **Исправления автора.** Загрузка исправленных файлов и ответ рецензентам; редакторы получают уведомление.
- **Отзыв рукописи автором.** Рецензенты, которые ещё работают, получают письмо, что рецензия больше не нужна.
- **Обсуждения** между авторами и редакторами по рукописи, с уведомлениями по почте.
- **История:** решения с письмами и журнал всех писем по рукописи (для редакции). Личные ссылки для входа в журнале писем не сохраняются.
- **Настройки** (администратор):
  - рецензирование: метод, сроки, напоминания, инструкция для рецензентов;
  - конструктор форм рецензии;
  - редактор шаблонов писем: подстановки проверяются, в письмах рецензентам нельзя использовать имена авторов.
- **Страницы:**
  - «My reviews» для рецензентов;
  - страница рукописи с этапами, решениями, раундами, обсуждениями и историей;
  - фильтры очереди редакции по этапу и «назначено мне».

### Этап 2 — подача рукописей

- **Мастер подачи** из пяти шагов, прогресс сохраняется на каждом:
  1. Раздел, чек-лист требований журнала, комментарий редактору.
  2. Файлы.
  3. Название, аннотация (с лимитом слов), ключевые слова, список литературы, финансирование,
     конфликт интересов.
  4. Авторы.
  5. Проверка и отправка.

  Пока черновик не готов, мастер показывает, чего не хватает, и ведёт к нужному шагу.
- **Соавторы.**
  - Порядок в списке авторов и автор для переписки.
  - ORCID, аффилиация, страна.
  - Можно указать участников, которые только упоминаются в благодарностях.
  - Соавторы получают уведомление о подаче.
- **Файлы** загружаются браузером прямо в хранилище по подписанной ссылке, минуя API.
  - Перед загрузкой проверяются размер и расширение.
  - После загрузки worker проверяет содержимое по сигнатуре и считает sha256.
  - Файл с неверным содержимым (например, текст, переименованный в .pdf) отклоняется с объяснением.
  - Брошенные загрузки удаляются автоматически.
- **Номер рукописи** присваивается при отправке: `JRN-2026-0001` (префикс задаётся в настройках).
  Автору приходит подтверждение, главному редактору и редакторам раздела — уведомление.
- **Проверка на заимствования.**
  - Общий интерфейс для сервисов проверки и тестовый провайдер со случайными процентами.
  - Автоматический запуск при подаче и порог «требует внимания» задаются в настройках.
  - Результат видит только редакция.
  - Настоящий провайдер (Crossref Similarity Check) подключается, когда у журнала будет к нему доступ.
- **Очередь редакции.**
  - Поиск по номеру и названию, фильтры по статусу и разделу, процент совпадений.
  - Главный редактор видит все рукописи, редактор раздела — только рукописи своих разделов.
  - Редактор не видит в редакционном режиме рукописи, где он сам автор.
- **Настройки подачи** (администратор):
  - чек-лист;
  - требования к авторам;
  - лимиты размера файлов, слов в аннотации и ключевых слов;
  - префикс номера;
  - проверка на заимствования.

### Этап 1 — каркас

- **Учётные записи.** Регистрация с согласиями на обработку персональных данных и их передачу за рубеж
  (закон РК), подтверждение e-mail, вход, выход, восстановление пароля, смена пароля, профиль с ORCID.
- **Безопасность.**
  - Пароли хранятся в Argon2id.
  - Сессии хранятся на сервере, cookie недоступна скриптам (httpOnly).
  - Защита от CSRF.
  - Блокировка учётной записи после 10 неудачных попыток входа.
  - Ограничение частоты запросов в nginx.
- **Журнал.** Настройки (название, ISSN с проверкой контрольной цифры, издатель, контакты). Защита от
  одновременной правки двумя людьми: изменения второго отклоняются, данные первого не теряются.
- **Разделы журнала** и назначение их редакторов.
- **Роли и права.** Администратор, главный редактор, редактор раздела, рецензент, автор, литературный
  редактор, верстальщик, корректор, финансовый менеджер.
- **Пользователи.** Поиск, приглашение по e-mail, изменение ролей, блокировка. Нельзя удалить последнего
  администратора.
- **Журнал аудита** всех важных действий.
- **Фоновые задачи.** Письма отправляются в фоне через очередь на PostgreSQL, с повторами при ошибках.
- **Рабочее пространство редакции** (React): вход и регистрация, личный кабинет, страницы администратора.

Следующий этап — производство и публикация: редактура, гранки, выпуски, DOI (см. план в §21 архитектуры).

## Структура

```
backend/              API и фоновые задачи (Python 3.13, FastAPI, SQLAlchemy, PostgreSQL)
  app/core/           общее: настройки, БД, ошибки, очередь задач, почта, безопасность
  app/modules/        модули: identity, journals, audit, notifications, submissions, files, similarity,
                      review (рецензирование), workflow (решения, редакторы, обсуждения),
                      payments (счета, оплата, возвраты, льготы; providers/ — адаптеры платёжных систем)
  migrations/         миграции базы данных (Alembic)
  tests/              тесты (на настоящем PostgreSQL)
workspace/            рабочее пространство редакции (React, Vite, Mantine)
packages/api-client/  типизированный клиент API, генерируется из схемы OpenAPI бэкенда
deploy/nginx/         nginx: раздача интерфейса, прокси к API, заголовки безопасности, лимиты
compose.yaml          всё приложение в Docker одной командой
docs/                 архитектура
```

## Запуск в Docker

Нужен Docker с Compose.

```bash
docker compose up --build
```

```bash
docker compose run --rm api python -m app.cli seed-demo
```

- Рабочее пространство: http://localhost:8080
- Отправленные письма (Mailpit): http://localhost:8025
- Документация API: http://localhost:8080/api/docs

## Запуск для разработки (без Docker)

Нужны Python 3.13 с [uv](https://docs.astral.sh/uv/), Node.js 22.22+ и PostgreSQL 16+
с базой `jps` (пользователь и пароль `jps`).

```bash
cd backend && cp .env.example .env && uv sync
```

```bash
cd backend && uv run alembic upgrade head && uv run python -m app.cli seed-demo
```

```bash
cd backend && uv run uvicorn app.main:create_app --factory --reload
```

```bash
cd backend && uv run python -m app.worker
```

```bash
npm install && npm run dev
```

Рабочее пространство откроется на http://localhost:5173. Письма в режиме разработки печатаются в журнал
процесса `app.worker`.

## Настоящий журнал: первый запуск

Создать журнал и первого администратора (пароль спросит или возьмёт из `JPS_ADMIN_PASSWORD`):

```bash
cd backend && uv run python -m app.cli bootstrap --journal-name "Название журнала" --admin-email you@example.org --admin-given-name Имя
```

Остальное (ISSN, контакты, разделы, редакторы) настраивается в рабочем пространстве.

## Проверки

```bash
cd backend && uv run ruff check . && uv run ruff format --check . && uv run mypy app tests && uv run lint-imports && uv run pytest
```

```bash
npx biome check . && npm run check && npm test && npm run build
```

Тесты бэкенда используют базу `jps_test` (адрес можно задать в `JPS_TEST_DATABASE_URL`).
Те же проверки запускает CI (`.github/workflows/ci.yml`). Отдельная проверка в CI следит, чтобы клиент API
был перегенерирован после изменения бэкенда.

После изменения API перегенерируйте клиент:

## Настройки

Все настройки бэкенда — переменные окружения с префиксом `JPS_`. Полный список с пояснениями — в
`backend/app/core/config.py`, пример — `backend/.env.example`. Основные:

| Переменная | Назначение |
|---|---|
| `JPS_DATABASE_URL` | подключение к PostgreSQL |
| `JPS_WORKSPACE_URL` | адрес рабочего пространства для ссылок в письмах |
| `JPS_COOKIE_SECURE` | `true` в production (cookie только по HTTPS) |
| `JPS_EMAIL_BACKEND` | `smtp` в production, `console` при разработке |
| `JPS_SMTP_HOST`, `JPS_SMTP_PORT`, `JPS_SMTP_USERNAME`, `JPS_SMTP_PASSWORD` | почтовый сервер |
| `JPS_EMAIL_FROM` | адрес отправителя писем |
| `JPS_SECRET_KEY` | секрет для подписи ссылок на файлы; в production — не меньше 32 случайных символов |
| `JPS_STORAGE_BACKEND` | `s3` в production, `local` при разработке (файлы в `JPS_STORAGE_LOCAL_PATH`) |
| `JPS_S3_ENDPOINT_URL`, `JPS_S3_BUCKET`, `JPS_S3_REGION`, `JPS_S3_ACCESS_KEY_ID`, `JPS_S3_SECRET_ACCESS_KEY` | S3-совместимое хранилище файлов |
| `JPS_SIMILARITY_PROVIDER` | `disabled` или `fake` (тестовый провайдер, только для разработки) |
| `JPS_PAYMENTS_TEST_PROVIDER` | тестовая страница оплаты картой (только для разработки) |
| `JPS_PAYPAL_MODE`, `JPS_PAYPAL_CLIENT_ID`, `JPS_PAYPAL_CLIENT_SECRET`, `JPS_PAYPAL_WEBHOOK_ID` | PayPal; адрес для уведомлений: `https://<домен>/api/v1/payments/webhooks/paypal` |
| `JPS_CROSSREF_MODE`, `JPS_CROSSREF_USERNAME`, `JPS_CROSSREF_PASSWORD` | регистрация DOI: `disabled`, `fake` (разработка), `test`, `production` |
| `JPS_SITE_REVALIDATE_URL`, `JPS_SITE_REVALIDATE_SECRET` | куда сообщать сайту журнала об изменениях и общий секрет для подписи |
| `JPS_PUBLIC_CACHE_SECONDS`, `JPS_PUBLIC_STALE_SECONDS` | сколько кэши хранят ответы публичного API |

С `JPS_ENVIRONMENT=production` приложение не запустится в таких случаях:
- cookie не защищены;
- почта не настроена;
- секрет оставлен по умолчанию или короче 32 символов;
- файлы хранятся не в S3;
- включён тестовый провайдер проверки на заимствования или тестовый платёжный провайдер;
- PayPal настроен не в боевом режиме;
- включён режим `fake` для Crossref;
- задан адрес сайта для обновления страниц, но не задан секрет.

### Хранилище файлов

При разработке файлы лежат на диске. API выдаёт браузеру подписанные ссылки на `/api/v1/storage/…`;
в nginx для этого пути разрешены запросы до 200 МБ.

В production нужен приватный S3-бакет в Казахстане (закон о персональных данных, см. §17 архитектуры).
Браузер загружает файлы прямо в бакет. Для этого в бакете настраивается CORS:
- разрешены методы `PUT` и `GET`;
- разрешён заголовок `Content-Type` (`Content-Length` браузер ставит сам, он тоже входит в подпись ссылки);
- источник — адрес рабочего пространства.

Кроме того, адрес бакета нужно добавить в `connect-src` политики CSP в `deploy/nginx/workspace.conf`,
иначе браузер не даст отправить файл на другой домен.
